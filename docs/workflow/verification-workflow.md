# 검증 워크플로

다섯 게이트가 각각 무엇을 언제 판정하는지를 한 장으로 정리한다.

설계 근거와 상세는 [qa-llm-verification.md](../software-quality/qa-llm-verification.md)에 있다.
이 문서는 그 설계가 실제로 어떻게 흐르는지를 보기 위한 참조용이다.

## 전체 흐름

```
                              개발자
                                |
                    +-----------+-----------+
                    |      코드 작성        |
                    +-----------+-----------+
                                |  git commit
                                v
     +======================================================+
     |  G-LOCAL           Claude, 로컬, 개발자 재량         |
     |  범위: 마지막 커밋의 변경분                          |
     +------------------------------------------------------+
     |  1. ./gradlew check    커버리지, 정적분석  -> 알림만  |
     |  2. LLM 판정           활성화 항목 전부    -> 알림만  |
     +======================================================+
                                |  고침, 재커밋 (반복)
                                |
                                |  git push
                                v
     +======================================================+
     |  G-BUILD           Gradle, SonarQube, 자동           |
     +------------------------------------------------------+
     |  커버리지  service 패키지 메서드 100%                |
     |  정적분석  신규 Blocker 0건                          |
     |                                          * 병합 차단 |
     +======================================================+
                    실패 ------+------ 통과
                     |                  |
                 여기서 멈춤            v
                            +==========================================+
                            |  G-PR      gemini-2.5-flash, 자동        |
                            |  범위: PR 누적 diff (base...HEAD)        |
                            +------------------------------------------+
                            |  1단계  backend 250건        항상        |
                            |           |                              |
                            |           +- 응답이 온전한가?            |
                            |           |    아니오 -> 나머지 UNJUDGED |
                            |           v 예                           |
                            |  2단계  common+infra 214건   조건부      |
                            |                              비차단      |
                            +==========================================+
                                              |
                                        리뷰 코멘트
                                              |
                                          병합 후
                                              v
     +======================================================+
     |  G-RELEASE         배포와 시험 스크립트, 배포 직전   |
     |  RDS available / 대상그룹 healthy / 인증서 30일 등   |
     |                                          * 배포 차단 |
     +======================================================+

     +======================================================+
     |  G-AUDIT           주기별, 1시간부터 6개월까지       |
     |  기록 존재 확인 -> 티켓 생성              비차단     |
     +======================================================+
```

**차단하는 것은 도구가 판정하는 두 게이트뿐이다.**
G-BUILD와 G-RELEASE는 결정론적이라 오탐이 없고, LLM 게이트는 재현율이 미측정이라 차단하지 않는다.

## 게이트별 검증 카테고리

### G-BUILD (도구, 차단)

| 카테고리 | 기준 | 판정 주체 |
|---|---|---|
| 커버리지 | `*.domain.service.*` 메서드 **100%** | Gradle JaCoCo |
| 정적 분석 | 신규 **Blocker 0건** | SonarQube |

`Blocker`는 프로덕션에서 애플리케이션을 망가뜨릴 높은 확률의 버그를 뜻한다. 병합을 막을 근거가 되는 것은 이 등급뿐이다.
`INF-10-*` 10건이 이 설정 자체를 점검한다.

### G-PR 1단계: backend 250건 (항상)

| 접두사 | 카테고리 | 건수 |
|---|---|---|
| `API` | API 설계 (Google AIP) | 62 |
| `EJ` | Effective Java | 50 |
| `EC` | 엔티티 생성 패턴 | 31 |
| `DPB` | 도메인 패키지 경계 | 29 |
| `IDS` | 식별자 전략 | 25 |
| `UT` | 단위 테스트 | 20 |
| `BE` | 베이스 엔티티 | 18 |
| `JPA` | JPA 사용 (RDB 관점) | 15 |

**"어떻게 쓰는가"** 를 다룬다. 코드 관용과 패턴이다.

### G-PR 2단계: common + infra 214건 (조건부)

| 접두사 | 카테고리 | 활성화 |
|---|---|---|
| `INF` | 인프라 제약 | 53 |
| `REL` | 신뢰성 | 25 |
| `SEC` | 보안 | 23 |
| `OBS` | 관측 가능성 | 19 |
| `PERF` | 성능 효율성 | 18 |
| `CMP` | 호환성 | 17 |
| `DI` | 데이터 정합성 | 17 |
| `FUN` | 기능 적합성 | 14 |
| `MNT` | 유지보수성 | 13 |
| `FLX` | 유연성과 확장성 | 12 |
| `TRD` | 트레이드오프 | 3 |

**"얼마나 잘 하는가"** (품질 속성)와 **"이 인프라가 강제하는 것"** 을 다룬다.

2단계를 조건부로 둔 이유는 `gemini-2.5-flash`가 464건을 온전히 처리하는지 측정된 바 없기 때문이다.
1단계 응답이 온전할 때만 진행하고, 건너뛴 항목은 `UNJUDGED`로 기록해 통과와 구분한다.

### G-LOCAL: 위 전부

빌드 게이트와 두 단계를 모두 돌리되 차단하지 않는다.
작업 중 반복 실행하는 도구이므로 중간 상태에서 실패하는 것이 정상이다.

### G-RELEASE: `PRE` 13건 (차단)

RDS 상태, 대상 그룹 healthy 수, 인증서 잔여일, CPU 크레딧 잔량 등이다.
**런타임 조회가 필요해 LLM이 아니라 스크립트가 판정한다.**

### G-AUDIT: `INC` 37 + `OPS` 34 등

주기별로 **기록 존재**만 확인한다.
"복원 리허설을 수행했는가"는 판정할 수 없고 "기록 파일이 있고 기한 내인가"는 판정할 수 있다.

## 카테고리가 어디서 오는가

```
LGU-2/.github  docs/software-quality/    217건   품질 속성 (ISO 25010 기반)
LGU-2/backend  docs/code-architecture/   250건   코드 관용과 패턴
LGU-2/infra    docs/infra-review/        100건   인프라 결정이 코드에 부과하는 제약
                                         -----
                                         567건
```

**판정 기준은 세 저장소에서 오지만 판정 대상은 backend 코드 하나다.**
`anchors.yml`이 backend에만 있기 때문이며, Terraform이 생기면 infra에도 만든다.

## 활성화는 앵커 규칙이 정한다

변경 파일이 규칙을 트리거하고, 규칙이 어떤 항목을 켤지 정한다.

```
**/domain/service/*.java   ->  DI PERF REL DPB EJ FUN MNT FLX TRD INF(1,2,8장)
**/domain/entity/*.java    ->  BE EC JPA DI CMP IDS INF(8장)
**/domain/controller/*.java ->  SEC CMP API DPB EJ FUN IDS
**/domain/client/**/*.java ->  REL DPB OBS INF(3장)
application*.yml           ->  REL PERF OBS FLX SEC INF(3,4,5,7,9장)
db/migration/*.sql         ->  DI CMP FLX BE IDS INF(6장)
src/test/**/*Test.java     ->  UT MNT
build.gradle               ->  MNT PERF INF(10장)
```

567건 중 **464건**이 어떤 규칙엔가 걸린다.
나머지 103건은 `INC` 37, `OPS` 34, `PRE` 13 등으로 **G-AUDIT과 G-RELEASE 소관이라 PR로 트리거되지 않는 것이 정상**이다.

수치의 재현 방법은 [qa-llm-verification.md](../software-quality/qa-llm-verification.md) 9.2절에 있다.

## 진입점부터의 실행 순서

앞 절이 "언제 무엇을 판정하는가"라면, 이 절은 **"어떤 파일을 순서대로 읽는가"**다.

`[없음]`은 아직 만들지 않은 파일을 뜻한다. 설계상 필요하다고 정해졌으나 디스크에 존재하지 않는다.

```
  [진입점]  PR 생성 또는 push
      |
      v
+- 1 --------------------------------------------------------------+
|  backend/.github/workflows/llm-verify.yml            [ 없음 ]    |
|  트리거만 정의. 본체를 부른다                                    |
|    on: pull_request [opened, synchronize, reopened]              |
|    uses: LGU-2/.github/.github/workflows/llm-verify.yml@v1       |
+--------------------------+---------------------------------------+
                           v
+- 2 --------------------------------------------------------------+
|  common/.github/workflows/llm-verify.yml             [ 없음 ]    |
|  본체. 아래 3~16 을 수행한다                                     |
+--------------------------+---------------------------------------+
                           v
+- 3  체크아웃 -----------------------------------------------------+
|  backend  @HEAD   fetch-depth: 0      판정 대상                  |
|  common   @base   점검 항목과 레지스트리                         |
|  infra    @base   확정값 (조건부. 10단계에서 결정)               |
+--------------------------+---------------------------------------+
                           v
+- 4  범위 산출 ----------------------------------------------------+
|  읽음: git                                                       |
|    판정 범위   git diff origin/main...HEAD    (누적. 안 좁힘)    |
|    재판정 범위 git diff $BEFORE..HEAD         (증분. 캐시용)     |
|    force push 면 조상 검사 실패 -> 캐시 버리고 전량 재판정       |
+--------------------------+---------------------------------------+
                           v
+- 5  앵커 규칙 로드 -----------------------------------------------+
|  읽음: backend/.github/llm-verify/anchors.yml        [ 있음 ]    |
|    규칙 11개                                                     |
+--------------------------+---------------------------------------+
                           v
+- 6  규칙 매칭 ----------------------------------------------------+
|  변경 파일 x trigger  ->  매칭된 규칙                            |
|    산출 1  anchors      함께 읽을 파일 목록                      |
|    산출 2  activate     prefixes / levels / chapters             |
|    산출 3  needs_baseline_values                                 |
+--------------------------+---------------------------------------+
                           v
+- 7  레지스트리 로드 ----------------------------------------------+
|  읽음: common/.github/llm-verify/items.yml    217건  [ 있음 ]    |
|        backend/.github/llm-verify/items.yml   250건  [ 있음 ]    |
|        infra/.github/llm-verify/items.yml     100건  [ 있음 ]    |
|                                              ------              |
|                                               567건              |
+--------------------------+---------------------------------------+
                           v
+- 8  필터 --------------------------------------------------------+
|  567  --prefixes-->  --levels-->  --chapters-->  활성 ID 목록    |
|                                                                  |
|  예) controller 규칙이면 214건                                   |
+--------------------------+---------------------------------------+
                           v
+- 9  판정 기준 본문 로드 ------------------------------------------+
|  활성 항목이 속한 문서만 읽는다 (items.yml 의 doc 필드)          |
|    common/docs/software-quality/qa-*.md              [ 있음 ]    |
|    backend/docs/code-architecture/*-guideline.md     [ 있음 ]    |
|    infra/docs/infra-review/code-guideline.md         [ 있음 ]    |
+--------------------------+---------------------------------------+
                           v
+- 10  확정값 로드 -------------------------------------------------+
|  needs_baseline_values: true 인 규칙이 하나라도 걸릴 때만        |
|    infra/docs/system-design/*.md                     [ 있음 ]    |
|                                                                  |
|  아니면 3단계의 infra 체크아웃 자체를 건너뛴다                   |
+--------------------------+---------------------------------------+
                           v
+- 11  앵커 파일 로드 ----------------------------------------------+
|  6단계가 정한 파일들. diff 에 없어도 읽는다                      |
|    부재 판정("타임아웃이 없다")이 성립하는 근거                  |
|    못 읽으면 INSUFFICIENT_EVIDENCE                               |
+--------------------------+---------------------------------------+
                           v
+- 12  알려진 모순 로드 --------------------------------------------+
|  읽음: common/.github/llm-verify/known-conflicts.yml [ 없음 ]    |
|    목록에 있으면 재지적하지 않는다                               |
+--------------------------+---------------------------------------+
                           v
+- 13  기준선 판정 -------------------------------------------------+
|  base 커밋에 같은 판정. base SHA 로 캐시                         |
|    base OK + head VIOLATION  ->  이 PR 이 만든 것                |
|    base VIOLATION 도 있음    ->  기존 부채                       |
+--------------------------+---------------------------------------+
                           v
+- 14  LLM 호출 1단계 ----------------------------------------------+
|  ci_stage: 1 인 활성 항목 (backend 250 중)                       |
|  전체 1회 호출. 정해진 출력 구조로만 응답                        |
+--------------------------+---------------------------------------+
              +------------+------------+
              | 응답 검증                |
              |  finishReason 정상?      |
              |  응답 수 == 요청 수?     |
              |  파싱 성공?              |
              |  토큰 여유?              |
              +------+------------+------+
            아니오   |            |  예
                     v            v
        나머지 UNJUDGED    +- 15  LLM 호출 2단계 --------------+
                     |     |  ci_stage: 2 (common+infra 214)  |
                     +---->+--------------+--------------------+
                                          v
+- 16  필터링과 출력 -----------------------------------------------+
|  defers_to 억제  ->  캐시 히트 제외  ->  기존 코멘트 중복 제외   |
|  신규 위반 위로, 기존 부채 접어서, UNJUDGED 목록 병기            |
|  차단 없음                                                       |
+------------------------------------------------------------------+
```

### 단계별로 읽는 파일

| 단계 | 읽는 것 | 산출 | 상태 |
|---|---|---|---|
| 1 | 호출자 워크플로 | 본체 호출 | **없음** |
| 2 | 본체 워크플로 | 이하 전부 수행 | **없음** |
| 3 | git (3개 저장소) | 작업 트리 | - |
| 4 | git diff | 판정 범위, 재판정 범위 | - |
| 5 | `anchors.yml` | 규칙 11개 | 있음 |
| 6 | (계산) | 앵커 목록, 활성 조건 | - |
| 7 | `items.yml` x 3 | 567건 | 있음 |
| 8 | (계산) | 활성 ID 목록 | - |
| 9 | 가이드 문서 | 항목 본문과 설명 | 있음 |
| 10 | system-design | 확정값 | 있음 (조건부) |
| 11 | 앵커 파일 | 판정 맥락 | - |
| 12 | `known-conflicts.yml` | 억제 목록 | **없음** |
| 13~15 | (LLM) | 판정 결과 | - |
| 16 | 캐시, 기존 코멘트 | 최종 출력 | - |

### 데이터가 좁혀지는 과정

```
567건  세 저장소의 전체 점검 항목
  |
  |  prefixes   규칙이 지정한 문서군만
  v
  |  levels     코드/설계/인프라/프로세스 중 지정된 것만
  v
  |  chapters   장 번호로 범위 축소 (INF 53건을 규칙당 3~24건으로)
  v
214건  controller 규칙의 활성 항목
  |
  |  ci_stage   1단계와 2단계로 분할
  v
1단계 + 2단계
```

### 5, 7, 9 를 분리한 이유

```
anchors.yml   "무엇을 켤지"      규칙
items.yml     "그게 무엇인지"    메타데이터 (level, gate, domains, ci_stage, defers_to)
가이드 문서   "왜 그런지"        본문과 예시
```

셋을 한 파일에 두면 규칙 하나를 고칠 때 문서를 건드리게 되고, 문서 한 줄을 고칠 때 규칙이 깨진다.

**`items.yml`은 문서에서 자동 생성한다.** 문서가 원본이고 레지스트리는 파생물이므로, 문서를 고치면 재생성해야 한다.

### 지금 끊겨 있는 곳

| 위치 | 없는 파일 | 없으면 |
|------|-----------|--------|
| 1, 2단계 | 워크플로 두 개 | **PR 이 열려도 아무 일도 일어나지 않는다** |
| 12단계 | `known-conflicts.yml` | 확정값 모순 4건이 매 PR 마다 재지적된다 |
| G-LOCAL | `backend/.claude/commands/verify.md` | 로컬 검증 절차를 개발자가 매번 조립해야 한다 |

**5~11 단계의 데이터는 전부 준비되어 있고, 그것을 읽어 실행할 코드가 없는 상태다.**
