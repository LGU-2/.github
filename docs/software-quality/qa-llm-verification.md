# LLM 기반 품질 검증 설계

이 문서군의 점검 항목을 LLM으로 자동 판정하려 할 때의 설계 방안과 그 한계를 다룬다.

다른 문서가 "무엇을 점검하는가"를 정한다면, 이 문서는 "그 점검을 누가 어떻게 수행하는가"를 정한다.
품질 속성 문서가 아니므로 ISO/IEC 25010과의 매핑은 없다.

> **수치에는 근거 등급이 표시되어 있다.**
> A는 산술로 도출된 값, B는 출처가 있는 값(링크 표기), C는 근거 없이 정한 예시값이다.
> C로 표시된 값은 그대로 채택하지 말고 측정 후 팀이 확정한다.
> 등급 정의는 quality-attributes.md의 "판정 기준 수치의 성격"을 참고한다.

## 1. 판정 가능성을 지배하는 세 가지 제약

설계에 앞서 이 문서군의 실제 구성을 집계했다.
아래 세 절의 수치는 문서를 세어 얻은 값이므로 등급 A다. 재현 방법은 9장에 있다.

### 1.1 점검 항목의 71%가 코드 밖에 있다

`qa-*.md` 11개 문서의 불릿 점검 항목은 223건이며, 층위별 분포는 다음과 같다 (등급 A).

| 층위 | 건수 | 비중 |
|------|------|------|
| `[코드]` | 65 | 29.1% |
| `[설계]` | 65 | 29.1% |
| `[인프라]` | 42 | 18.8% |
| `[프로세스]` | 51 | 22.9% |

quality-attributes.md가 명시하듯 PR 단위로 판정할 수 있는 것은 `[코드]` 항목뿐이다.
따라서 **PR diff만 입력으로 주는 LLM 검증은 29%가 상한이다.**
나머지 71%를 판정하려면 LLM을 개선하는 것이 아니라 입력을 바꿔야 한다.

### 1.2 점검 항목의 86%가 부재를 묻는다

점검 항목을 문장 형태로 나누면 다음과 같다 (등급 A).

| 형태 | 예 | 건수 | 비중 |
|------|-----|------|------|
| 부정형 (있는 것을 지적) | "쿼리를 문자열 연결로 조립하지 않는가" | 32 | 14.3% |
| 긍정형 (없는 것을 지적) | "모든 외부 호출에 타임아웃이 설정되어 있는가" | 191 | 85.7% |

층위별로 보면 더 뚜렷하다.

| 층위 | 부정형 | 긍정형 |
|------|--------|--------|
| `[코드]` | 21 | 44 |
| `[설계]` | 3 | 62 |
| `[인프라]` | 3 | 39 |
| `[프로세스]` | 5 | 46 |

이 분포가 설계의 핵심 과제를 결정한다.
LLM은 diff에 **있는** 코드를 평가하는 데는 강하지만, diff에 **없는** 것을 알아채는 데는 현저히 약하다.
"타임아웃이 없다", "예외 경로가 비어 있다", "인덱스가 없다"는 모두 보이지 않는 것을 보는 판정이다.

부재 판정을 그대로 두면 재현율이 낮고, 낮은 재현율은 "통과했으니 괜찮다"는 잘못된 신호를 준다.
이것이 오탐보다 위험하다. 3장과 4장은 이 문제에 대한 대응이다.

### 1.3 판정 기준 수치의 대부분이 등급 C다

이 문서군의 임계치 대부분은 근거 없이 정한 예시값이다.
따라서 **LLM에게 값의 옳고 그름을 판정시켜서는 안 된다.**

| 질문 | 판정 | 이유 |
|------|------|------|
| "커넥션풀 30은 적절한가" | 불가 | 등급 C 값이다. LLM에게 정답이 없다 |
| "커넥션풀 값이 명시되어 있는가" | 가능 | 설정 파일에 증거가 있다 |
| "그 값의 산정 근거가 기록되어 있는가" | 가능 | ADR 존재 여부로 판정한다 |

구조 판정과 값 판정을 섞으면, LLM이 근거 없는 숫자를 근거 있는 것처럼 단정하게 된다.
등급 C 수치에 대해 LLM이 낼 수 있는 판정은 "정해졌고 기록되었는가"까지다.

## 2. 4단 게이트

층위마다 증거가 나타나는 시점과 형태가 다르다.
한 게이트에 전부 밀어 넣으면 `[프로세스]` 항목까지 PR 리뷰 지적처럼 보여 소음이 된다.
문서군이 층위 표기를 도입한 것과 같은 이유로 게이트도 나눈다.

| 게이트 | 시점 | 입력(증거) | 담당 층위 | 차단 |
|--------|------|-----------|-----------|------|
| G-PR | PR 생성 시와 이후 매 push (2.4절) | diff + 변경 파일 전체 + 앵커 파일(3장) | `[코드]`, `[인프라]` 일부 | 차단 |
| G-DESIGN | 스키마, 계약, 의존성 변경 감지 시. G-PR과 같은 시점 | 마이그레이션 SQL, API 계약 diff, ADR | `[설계]` | 비차단. ADR 요구 |
| G-RELEASE | 배포 직전 | 부하 테스트 결과, 호환성 리포트, 롤백 가능성 | `[설계]`, `[프로세스]` 일부 | 차단 |
| G-AUDIT | 주기별. 1시간부터 6개월까지 (2.5절) | 운영 메트릭, 슬로우 쿼리 로그, 알림 이력, 기록물 | `[프로세스]` | 비차단. 티켓 생성 |

G-DESIGN은 G-PR과 시점이 같다. 별도 게이트로 둔 것은 담당 층위와 차단 여부가 다르기 때문이며, 실행 시점이 다른 것이 아니다.
G-RELEASE를 릴리스 태그 시점이 아니라 배포 직전에 두는 이유는, 태그를 찍은 뒤 차단하면 되돌리는 비용이 크고 성능 효율성 문서가 요구하는 것이 "주요 릴리스 **전**의 부하 테스트"이기 때문이다.

점검 항목
* `[프로세스]` 차단 게이트가 G-PR과 G-RELEASE로 한정되어 있는가
* `[프로세스]` 비차단 게이트의 지적이 티켓으로 남아 추적되는가
* `[인프라]` 게이트별로 활성화되는 점검 항목 목록이 분리되어 있는가

차단 게이트를 늘리면 배포가 막히고, 곧 우회 문화가 생긴다.
우회가 관행이 되는 순간 나머지 게이트의 신뢰도까지 떨어진다.

### 2.1 판정 기준은 두 층으로 나뉘어 있다

판정에 필요한 문서가 한 곳에 있지 않다.

| 층 | 내용 | 위치 |
|----|------|------|
| 점검 항목 | 무엇을 점검하는가. 수치는 대부분 등급 C 예시값 | `LGU-2/.github` 의 `docs/software-quality/` |
| 확정값 | 이 팀이 실제로 정한 목표치와 보장 메커니즘 | `LGU-2/infra` 의 `docs/system-design/` |

quality-attributes.md의 "도메인에 맞게 채워야 하는 부분"이 두 층의 관계를 규정한다.
앞 층이 빈칸을 만들고 뒤 층이 채운다.
예를 들어 신뢰성 문서는 RPO와 RTO 표를 등급 C로 제시하고, 확정값 문서가 시나리오별 실제 목표와 보장 메커니즘을 정한다.

**확정값 문서는 항상 필요한 것이 아니다.**
1.3절이 나눈 판정 유형에 따라 갈린다.

| 판정 유형 | 예 | 확정값 문서 |
|-----------|-----|-------------|
| 구조 판정 | "타임아웃이 설정되어 있는가" | 불필요 |
| 값 판정 | "타임아웃 3초가 적절한가" | 애초에 하지 않는다 (1.3절) |
| 근거 판정 | "그 값의 산정 근거가 기록되어 있는가" | 필요 |
| 일치 판정 | "설정값이 확정값과 같은가" | 필요 |

`[코드]` 항목은 대부분 구조 판정이다.
"쿼리를 문자열 연결로 조립하지 않는가", "예외를 삼키지 않는가", "소유권을 검증하는가"는 코드만 보면 판정되며 확정값 유무와 결과가 같다.

확정값이 필요한 것은 근거 판정과 일치 판정이고, 주로 `[설계]`와 `[인프라]` 항목이다.
7.1절에서 G3와 G4로 분류한 `[설계]` 30건이 대체로 여기 해당한다.

확정값이 없다고 해서 등급 C 예시값으로 판정하는 것이 아니다.
그 경우 값 판정을 하지 않을 뿐이며, 그것이 1.3절이 요구한 동작이다.

### 2.1.1 의존은 부분적이다

따라서 기준 저장소 체크아웃은 조건부로 건다.
활성화된 항목 집합에 근거 판정이나 일치 판정이 포함될 때만 확정값 문서를 가져온다.

```yaml
- uses: actions/checkout@v4
  if: needs.scope.outputs.needs-baseline-values == 'true'
  with: { repository: LGU-2/infra, path: .design }
```

효과가 두 가지다.
순수 코드 PR은 체크아웃이 한 번 줄고, 확정값 저장소의 장애가 코드 판정에 영향을 주지 않는다.

다만 필요하다고 판단했는데 가져오지 못한 경우는 실패로 처리한다 (2.3절 마지막 점검 항목).
조건부로 건너뛴 것과 필요한데 실패한 것은 다르다.

두 층이 서로 다른 저장소에 있으므로 아래 두 규칙이 필요하다.
같은 저장소에 있었다면 한 커밋으로 묶여 움직여서 필요 없었을 규칙이다.

### 2.2 규칙 1: 판정 기준은 base 시점의 것을 쓴다

확정값 문서가 `infra` 레포 안에 있으므로, `infra` PR은 **판정 대상과 판정 기준을 같은 diff에 담을 수 있다.**

```
infra PR 하나에서
  - 오토스케일링 Terraform 변경
  - 확정값 문서의 오토스케일링 목표도 함께 완화

기준선 비교 결과 -> 신규 위반 없음 -> 통과
```

기준을 낮추면서 코드도 같이 낮추면 게이트를 그대로 지나간다.
qa-tradeoffs.md 6장이 요구하는 기준 조정 절차(사유와 근거 데이터 기록)도 함께 우회된다.

이를 막기 위해 판정에 쓰는 기준을 시점으로 고정한다.

| 판정 | 대상 | 기준 |
|------|------|------|
| head 판정 | head 코드 | **base 시점**의 점검 항목과 확정값 |
| 기준선 판정 | base 코드 | **base 시점**의 점검 항목과 확정값 |

PR 안에서 기준을 바꿔도 그 PR 판정에는 반영되지 않고, 병합된 뒤 다음 PR부터 적용된다.
기준 완화와 그 혜택을 한 PR에서 동시에 받는 경로가 닫힌다.

### 2.3 규칙 2: 기준 변경은 판정과 분리해 표시한다

기준 변경 자체는 막지 않는다. 정상적인 활동이고 qa-tradeoffs.md가 절차까지 정해 두었다.
다만 판정 결과에 섞이면 사람이 알아채지 못하므로 별도로 드러낸다.

diff에 다음 경로가 포함되면 판정 결과와 무관하게 리뷰 코멘트에 명시한다.

```
docs/system-design/        확정값 변경
docs/software-quality/     점검 항목 변경
```

표시 내용은 어느 항목이 어떻게 바뀌었는지와 조정 사유가 기록되었는지 여부다.

점검 항목
* `[설계]` 판정에 쓰는 기준을 base 시점 것으로 고정하는가
* `[인프라]` 두 기준 저장소의 참조가 모두 특정 시점으로 고정되어 있는가
* `[코드]` 기준 문서 변경이 diff에 포함되면 별도로 표시하는가
* `[인프라]` 기준 저장소 접근 실패 시 판정을 통과시키지 않고 실패시키는가

마지막 항목이 중요하다.
기준 저장소를 가져오지 못했을 때 조용히 건너뛰면, 판정하지 않은 PR이 통과한 것처럼 보인다.
4장의 `INSUFFICIENT_EVIDENCE`를 `OK`로 뭉뚱그리지 않는 것과 같은 이유다.

### 2.4 G-PR 재실행 규칙

PR은 한 번 열리고 끝나지 않는다. 열려 있는 동안 push가 반복되므로 재실행 규칙이 필요하다.

트리거는 세 가지다.

| 이벤트 | 시점 |
|--------|------|
| `opened` | PR 생성 |
| `synchronize` | PR이 열려 있는 상태의 매 push |
| `reopened` | 닫았다 다시 열 때 |

여기서 **증분을 어디에 적용하느냐가 핵심이다.**
비용과 소음을 줄이려고 "변경분만 검증"으로 구현하면 1.2절의 부재 판정 문제가 그대로 돌아온다.

| 범위 | 무엇을 정하는가 | 증분 적용 | 이유 |
|------|----------------|----------|------|
| 판정 범위 | 무엇을 판정 대상으로 삼는가 | **적용 안 함** | 병합되는 것은 각 push의 변경분이 아니라 PR 전체의 누적 상태다 |
| 재판정 범위 | 무엇을 LLM에 다시 물을 것인가 | 적용 | 비용 절감 |
| 출력 범위 | 무엇을 코멘트로 올릴 것인가 | 적용 | 소음 제거 (6장 기준) |

판정 범위를 좁히면 두 가지가 깨진다.
push 1에서 통과한 항목을 push 3에서 다른 파일이 무너뜨려도 재판정되지 않고, push 1의 위반을 push 2에서 고쳐도 해소가 감지되지 않아 차단이 풀리지 않는다.

```bash
# 판정 범위. push 횟수와 무관하게 항상 동일하다
git diff --name-only origin/$BASE_REF...HEAD

# 재판정 트리거. 이번 push에서 실제로 바뀐 것
git diff --name-only $BEFORE..HEAD
```

재판정 범위를 좁히려면 이전 판정을 캐시해야 하고, 캐시 키를 잘못 잡으면 판정 범위를 좁힌 것과 같은 결과가 된다.

```
캐시 키 = (항목 ID, 대상 파일 해시, 그 항목이 참조한 앵커 파일들의 해시,
          점검 항목 문서 SHA, 확정값 문서 SHA)
```

무효화는 **앵커 관계를 역방향으로 탄다.**
어떤 파일이 X의 앵커였다면, 그 파일이 바뀔 때 X는 변경되지 않았더라도 재판정 대상이다.
3장 앵커 표 기준으로 `application*.yml` 변경은 관련 항목을 거의 전부 무효화하는데, 그것이 맞는 동작이다.

점검 항목
* `[인프라]` PR 생성과 이후 매 push에 모두 재실행되는가
* `[설계]` 판정 범위를 이번 push의 변경분으로 좁히지 않는가
* `[코드]` 캐시 키에 앵커 파일과 기준 문서의 해시가 포함되는가
* `[코드]` force push로 증분 범위를 신뢰할 수 없을 때 전량 재판정으로 넘어가는가

마지막 항목은 조용히 실패하기 쉽다.
force push 후에는 이전 SHA가 조상이 아니게 되어 증분 범위 계산이 어긋나므로, 조상 여부를 검사하고 아니면 캐시를 버린다.

### 2.5 G-AUDIT 주기

`[프로세스]` 항목은 주기가 제각각이다.
하나로 뭉뚱그리면 실제로 언제 무엇을 도는지 알 수 없게 되므로, 원본 문서가 정한 주기를 그대로 따른다.

| 주기 | 대상 | 출처 |
|------|------|------|
| 1시간 | 집계값 vs 원본 합계 대조 | 데이터 정합성 7장 |
| 일 1회 | 외부 시스템 대사, 금액 대사, 상태 이력 연속성, 고아 데이터 | 데이터 정합성 7장 |
| 월 1회 | 감사 로그 검토 | 보안 5장 |
| 분기 1회 | 알림 정기 점검, 복원 리허설, 도상 훈련, 결함 유형 분포 집계, LLM 오탐 집계 | 관측 가능성 6장, 신뢰성 4장, 인시던트 10장, 기능 적합성 6장, 이 문서 6장 |
| 반기 1회 | 페일오버 훈련, 장애 주입 | 인시던트 10장 |
| 6개월 | 완화한 기준 재검토 | 트레이드오프 6장 |

위 주기는 원본 문서에 근거가 있으므로 이 표에 별도 등급 표시를 하지 않는다.
원본에서의 등급은 각 문서를 따른다.

**확정값 층이 이 주기를 덮어쓸 수 있다.**
복원 리허설이 그 사례다. 신뢰성 문서는 분기 1회 이상을 제시하지만 확정값 문서(백업과 복원 4.1절)는 **주 1회**로 정했다.
2.1절의 두 층 관계에 따라 확정값이 있으면 그쪽을 따른다. 이 표는 확정값이 없을 때의 기본값이다.

**LLM이 검사를 수행하는 것이 아니다.**
1시간과 일 1회 정합성 검사는 배치 잡의 영역이고, G-AUDIT가 하는 일은 **그 배치가 존재하고 결과가 기록되었는가**를 확인하는 것이다.
월 이상 주기의 항목도 마찬가지로 수행 기록의 존재를 본다.

이 구분이 흐려지면 7.1절의 G3와 G4를 잘못 분류하게 된다.
기록을 읽는 것은 가능하고, 그 기록이 성실했는지 판정하는 것은 불가능하다.

점검 항목
* `[프로세스]` 주기별로 무엇이 언제 도는지 목록이 분리되어 있는가
* `[인프라]` 각 주기의 실행 결과가 파일이나 티켓으로 남는가
* `[프로세스]` 기한이 지났는데 기록이 없는 항목을 검출하는가

## 3. 앵커 파일 주입

1.2절의 부재 판정 문제에 대한 직접적인 대응이다.
diff만 주면 "타임아웃이 없다"를 알 수 없으므로, 판정에 필요한 파일을 함께 동봉한다.

점검 항목
* `[인프라]` 변경 파일 유형별로 동봉할 앵커 파일이 규칙으로 정의되어 있는가
* `[설계]` 앵커 파일이 없을 때 판정을 보류하는 경로가 있는가
* `[인프라]` 동봉 규칙이 저장소 구조 변경에 따라 갱신되는가

앵커 규칙 (등급 C. 근거 없음. 저장소 구조에 맞게 정한다)

| 변경 파일 패턴 | 동봉할 앵커 파일 | 활성화할 문서 |
|----------------|-----------------|--------------|
| `**/*Controller.java` | SecurityConfig, 대상 Service, 응답 DTO | 보안, 호환성, 기능 적합성 |
| `**/*Repository.java`, `@Query` | 대상 엔티티, 관련 마이그레이션 SQL | 성능, 데이터 정합성 |
| `@Transactional` 포함 diff | 호출 대상 클래스, 외부 클라이언트 빈 정의 | 데이터 정합성, 신뢰성 |
| `db/migration/*.sql` | 대상 테이블 기존 DDL, 대응 엔티티 | 데이터 정합성, 호환성, 유연성 |
| `application*.yml` | 전 프로파일 yml, logback.xml, build.gradle | 성능, 신뢰성, 관측 가능성 |
| 외부 클라이언트 빈 정의 | resilience4j 설정, 타임아웃 설정 | 신뢰성 |

앵커 파일이 없으면 그 항목은 판정하지 않고 `INSUFFICIENT_EVIDENCE`로 표기한다.
추측으로 지적하면 오탐이 되고, 오탐이 쌓이면 팀이 전체를 무시하기 시작한다.
[qa-maintainability.md](./qa-maintainability.md)의 "거짓 경보가 반복되면 진짜 실패도 함께 묻힌다"가 그대로 적용된다.

## 4. 항목 ID와 출력 형식

자유 서술 리뷰를 금지한다.
LLM이 스스로 무엇을 볼지 고르게 두면, 눈에 띄는 것만 지적하고 부재 항목은 통째로 건너뛴다.

점검 항목
* `[설계]` 모든 점검 항목에 고유 ID가 부여되어 있는가
* `[코드]` 판정 출력이 정해진 구조를 따르는가
* `[코드]` 증거 위치가 없는 지적을 기계적으로 폐기하는가
* `[프로세스]` ID별로 판정 이력이 집계 가능한가

각 문서의 점검 항목에 `<문서약칭>-<장>-<순번>` 형식의 ID를 부여한다.
LLM은 활성화된 ID 목록을 순회하며 항목마다 다음 구조로만 답한다.

```json
{
  "id": "REL-2-01",
  "verdict": "VIOLATION",
  "evidence": "src/main/java/com/example/external/ExternalClient.java:23",
  "quote": "RestClient client = RestClient.create();",
  "reason": "연결 타임아웃과 읽기 타임아웃이 설정되지 않았다",
  "confidence": 0.9
}
```

`verdict`는 네 가지뿐이다.

| 값 | 의미 | 후속 처리 |
|----|------|-----------|
| `VIOLATION` | 위반 확인 | 차단 게이트면 차단 |
| `OK` | 충족 확인 | 기록만 |
| `NOT_APPLICABLE` | 이 변경과 무관 | 기록만 |
| `INSUFFICIENT_EVIDENCE` | 판정에 필요한 증거가 입력에 없음 | 앵커 규칙 보강 대상 |

이 구조가 세 가지를 동시에 해결한다.
부재 판정을 명시적 질문으로 바꾸어 재현율을 올리고, `evidence`가 없는 지적을 폐기해 환각을 억제하며, ID 단위 집계로 항목별 정확도 측정이 가능해진다.
마지막 것이 6장의 전제다.

`INSUFFICIENT_EVIDENCE`를 별도 값으로 둔 것이 중요하다.
이것을 `OK`로 뭉뚱그리면 "판정하지 못했다"가 "문제없다"로 둔갑한다.

## 5. 역할 분할

점검 항목
* `[설계]` 결정론적 도구가 판정할 수 있는 항목을 LLM에게 주지 않는가
* `[설계]` LLM이 값이 아니라 구조를 판정하도록 항목이 서술되어 있는가
* `[프로세스]` 사람만 판단할 수 있는 항목이 명시적으로 분리되어 있는가

| 주체 | 담당 | 원칙 |
|------|------|------|
| 결정론적 도구 | Checkstyle, SpotBugs, ArchUnit, SAST, EXPLAIN, 마이그레이션 린터 | 기계가 잡을 수 있는 것은 LLM에게 주지 않는다 |
| LLM 판정자 | 의미 판단이 필요한 것. 이름과 부수 효과의 불일치, 대체 동작의 안전성, 소유권 검증 누락, 호환 파괴 여부 | 값이 아니라 구조를 판정한다 |
| LLM 작성자 | ADR 초안, 런북 초안, 사후 분석 초안, 정합성 검사 쿼리 초안 | 판정하지 않는다. 사람의 입력 비용만 낮춘다 |
| 사람 | 등급 C 수치의 확정, 트레이드오프 선택, 완화 판단 | 위임 불가 |

[qa-maintainability.md](./qa-maintainability.md)는 "포맷터와 정적 분석 도구가 기계적으로 처리하면 사람은 도구가 못 잡는 설계와 로직에 집중할 수 있다"고 적었다.
LLM은 그 도구와 사람 사이의 빈칸만 맡는다.
ArchUnit이 이미 잡는 순환 참조를 LLM이 또 지적하면 같은 내용이 두 번 올라와 소음만 늘어난다.

## 6. 오탐 관리

[qa-observability.md](./qa-observability.md)의 알림 정기 점검 절차를 그대로 옮긴다.
LLM 리뷰도 알림과 같은 성질을 갖는다. 늘어나기만 하고 줄지 않으며, 정확도가 떨어지면 전체가 무시된다.

점검 항목
* `[프로세스]` LLM 지적의 항목별 정확도를 정기적으로 집계하는가
* `[프로세스]` 정확도가 낮은 항목을 제거하거나 보강하는 절차가 있는가
* `[프로세스]` 한 번도 발화하지 않은 항목을 확인하는가
* `[설계]` 차단 대상 항목이 정확도 기준을 충족하는가

```
분기 1회 수행

1. 지난 분기 LLM 지적 전수를 항목 ID별로 집계
2. ID별로 판정
   - 실제 수정으로 이어졌는가 (Y/N)
   - INSUFFICIENT_EVIDENCE 비율은 얼마인가
3. 정확도 30% 미만 항목 -> 프롬프트에서 제거하거나 앵커 파일 보강
4. 한 번도 발화하지 않은 항목 -> 트리거 조건이 잘못됐는지 확인
5. 사고는 났는데 지적이 없었던 구간 -> 항목 추가
6. 결과와 변경 내역 기록
```

판정 기준 (등급 C. 근거 없음. 3개월 측정 후 확정한다)

| 항목 | 예시값 | 정한 이유 |
|------|--------|-----------|
| 차단 항목의 최소 정확도 | 90% | 배포를 막는 판정은 틀리면 비용이 크다 |
| 비차단 항목의 최소 정확도 | 30% | 미달 시 제거 대상 |
| PR당 지적 건수 | 10건 이하 | 초과 시 읽히지 않는다 |
| `INSUFFICIENT_EVIDENCE` 비율 | 20% 이하 | 초과는 앵커 규칙 결함 |

판정하지 못하는 항목을 목록에 남겨 두면 나머지 항목의 신뢰도까지 떨어진다.
[qa-tradeoffs.md](./qa-tradeoffs.md)의 "지켜지지 않는 기준은 삭제한다"가 여기에도 적용된다.

## 7. 커버리지 계산

이 설계로 223건 중 몇 건을 실제로 판정할 수 있는지 계산한다.

이 장의 분류는 초판에서 한 차례 전면 개정되었다.
초판은 확정값 문서(`LGU-2/infra`의 `docs/system-design/`, 9개 문서 5,706줄)의 **존재를 모른 채** 작성되었고, ADR이 아직 없다는 전제로 계산했다.
실제로는 ADR 34건(INF-01~34)을 포함한 확정값 층이 이미 있었다.
7.2절이 그 실제 상태를, 7.3절 이후가 그것을 반영한 수치를 담는다.

### 7.1 항목별 판정 가능 등급

초판의 4등급으로는 실제 상태를 표현할 수 없어 5등급으로 나눈다.
초판의 G3(조건부)이 두 갈래로 갈리기 때문이다. 확정값이 실제로 적혀 있는 항목과, 문서는 있으나 값이 아직 비어 있거나 문서끼리 어긋나는 항목은 판정 가능성이 전혀 다르다.

| 등급 | 정의 | 판정 |
|------|------|------|
| G1 | 결정론적 도구가 판정 (SonarQube, JaCoCo) | 가능 |
| G2 | LLM 단독 판정. 증거가 코드 저장소에 완결 | 가능 |
| G3 | 확정값 문서를 참조해 판정. **확정값이 실제로 존재** | 가능 |
| G4 | 확정값이 미정이거나 문서 간 모순 | **현재 불가** |
| G5 | 구조적 판정 불가 (사람의 행위, 실측, 미래 예측) | 불가 |

분류 결과 (등급 C. 항목별 분류는 판단이 개입하므로 팀이 재검토한다)

| 층위 | 총계 | G1 | G2 | G3 | G4 | G5 |
|------|------|----|----|----|----|----|
| `[코드]` | 65 | 12 | 45 | 5 | 0 | 3 |
| `[설계]` | 65 | 3 | 22 | 20 | 10 | 10 |
| `[인프라]` | 42 | 2 | 25 | 6 | 4 | 5 |
| `[프로세스]` | 51 | 0 | 2 | 12 | 4 | 33 |
| 합계 | 223 | 17 | 94 | 43 | 18 | 51 |

초판 대비 두 방향으로 움직였다.

**G1이 23건에서 17건으로 줄었다.** 초판은 Checkstyle, SpotBugs, ArchUnit이 있다고 가정했으나, 확정 스택(기술 스택 문서 2.2절과 2.5절)에 그 셋이 없다.
정적 분석은 SonarQube Cloud, 커버리지는 JaCoCo 하나씩이다.
특히 **ArchUnit이 없어 도메인 경계와 순환 참조 판정이 도구에서 빠졌고**, 그만큼이 G2로 넘어와 LLM 부담이 늘었다.

**초판의 G3 61건이 G3 43건과 G4 18건으로 갈렸다.** 확정값 문서가 있다고 모든 값이 정해진 것은 아니다.

### 7.2 확정값 문서의 실제 상태

판정에 쓸 수 있는지는 확정값이 **적혀 있는가**로 갈린다. 세 부류가 섞여 있다.

#### 채워진 것

qa 문서가 등급 C로 비워 둔 자리를 확정값 문서가 실제로 채운 사례다.

| 점검 항목이 요구하는 것 | qa 문서의 등급 C 예시값 | 확정값 |
|------------------------|------------------------|--------|
| 가용성 목표 | 기능 등급별 99.5~99.95% | 장애 시나리오 9종별 RTO와 RPO, 보장 메커니즘까지 |
| 타임아웃 예산 | 게이트웨이 10s, 서비스 간 1s/5s | 종료 4계층(30/30/45/60초)과 요청 4계층(3/5/10/60초) |
| 커넥션풀 | `(DB 코어 x 2) + 디스크` | `maximum-pool-size: 10`, `minimum-idle: 10`, 인스턴스 수별 총량표 |
| 헬스체크 분리 | "liveness가 외부 의존성에 좌우되지 않는가" | liveness는 Docker, readiness는 ALB. 경로와 임계값까지 |
| 추적 샘플링 | 오류 100%, 핵심 10%, 일반 1% | 평상시 10%, 부하 시험 5%, 장애 주입 100%, 오류 100% |
| 복원 리허설 주기 | 분기 1회 이상 | **주 1회** (qa 기준보다 엄격) |
| 테스트 커버리지 | "목표로 삼지 않는다" | **service 패키지 메서드 100%, 미달 시 병합 차단** |
| 정적 분석 | 경고 0 | SonarQube Critical 이상 차단, 브랜치 보호로 강제 |
| 스키마 변경 | 4단계 확장 후 축소 | 동일 + 금지 DDL 4종 명시 + CI 차단 |
| 배포 롤백 | 예시 없음 | 롤백 트리거 5종과 각각의 동작 |

**복원 리허설과 커버리지 두 행이 중요하다.**
확정값 층이 qa 문서보다 **더 엄격한** 기준을 정한 사례이며, 확정값 층이 단순히 빈칸을 메우는 것이 아니라 판정 기준을 실제로 대체한다는 것을 보여 준다.

#### 아직 비어 있는 것

| 항목 | 상태 | 출처 |
|------|------|------|
| 알람 임계값 5곳 | `(미정)` 표기 | 알람과 알림 10.1절 |
| 오토스케일링 임계값 9항목 | 전부 `(미정)` | 오토스케일링 8절 |
| RDS `max_connections` | 미실측. 풀 크기와 인스턴스 상한의 전제 | 여러 문서 |
| PITR 실측 RTO, RPO | "근거 없는 목표치" 라고 문서가 명시 | 백업과 복원 4.2절 |
| 설정값 5종 | socketTimeout, 풀 크기, 트랜잭션 타임아웃, 톰캣 스레드, ALB 임계값 | 시스템 디자인 종합 13절 |
| QueryDSL 채택 | 미확정. 착수 전 스파이크 필요 | 기술 스택 3.8절 |

이 항목들에 걸린 점검 항목은 **근거 판정(기록이 있는가)은 가능하고 일치 판정(값이 같은가)은 불가능하다.**
"측정 전에는 경보 없이 관측만" 이라는 규율을 그대로 적용해 G4로 둔다.

#### 서로 어긋나는 것

같은 사실이 문서마다 다르게 적혀 있으면 판정 기준이 둘이 되어 어느 쪽으로도 판정할 수 없다.

| 항목 | 한쪽 | 다른 쪽 |
|------|------|---------|
| readiness 포함 대상 | 앱과 DB 장애 대응 1.1절: db 포함은 **잘못이며 철회**. 공유 의존성 제외 | 기술 스택 4.2절: `readiness: include: db, diskSpace` |
| 배포 중 용량 | 장애 대응 목표 7.1절: 50% | 무중단 배포 1절, 시스템 디자인 종합 7절: 100% |
| 배포 소요 | 장애 대응 목표 7.1절: 3~4분 | 무중단 배포 1절: 6~8분 |
| 혼재 구간 | 장애 대응 목표 7.1절: 약 2분, 7.4절: 약 3분 | 무중단 배포 8절: 약 1분 |

첫 행이 가장 위험하다.
철회된 설계가 다른 문서에 살아남아 있고, 그 문서가 **실행 가능한 yaml 형태**라 그대로 복사될 가능성이 높다.
공유 의존성을 readiness에 넣으면 DB 장애 시 전 인스턴스가 동시에 대상 그룹에서 빠지는데, 이는 두 문서가 공통으로 경계한 바로 그 실패 양상이다.

세 번째와 네 번째 행은 같은 문서 안에서도 어긋난다.
시스템 디자인 종합 7절 표는 혼재 1분인데 7.2절 본문은 2분이고, 7절 표는 용량 100%인데 7.3절 본문은 "용량이 절반이 되는데"다.

**이 유형은 LLM이 발견하기 좋은 결함이다.** 문서 전체를 한 번에 읽고 대조하는 작업이라 사람이 놓치기 쉽고 기계적으로 확인 가능하다.
G-AUDIT의 분기 항목으로 "확정값 문서 간 상호 모순 검출"을 두는 것이 실효가 있다.

### 7.3 재현율 할인

판정할 수 있다는 것과 매번 잡아낸다는 것은 다르다.

아래 재현율은 **전부 등급 C이며 근거가 없다.**
도입 후 3개월간 실측해 확정해야 한다. 측정 전에는 차단 없이 관측만 하는 상태로 둔다.

| 판정 유형 | 가정 재현율 | 근거 |
|-----------|------------|------|
| G1 결정론적 도구 | 0.98 | 규칙 기반이라 누락이 거의 없다 |
| G2 부정형 (있는 것 지적) | 0.85 | 안티패턴이 diff에 그대로 보인다 |
| G2 긍정형 (없는 것 지적) | 0.75 | 3장 앵커 주입과 4장 ID 순회 적용 시 |
| G3 확정값 대조 | 0.80 | 대조 대상이 명확하나 문서를 가로질러 찾아야 한다 |

G2 94건의 내부 구성은 부정형 약 28건, 긍정형 약 66건이다.

```
G1        : 17 × 0.98 = 16.7
G2 부정형 : 28 × 0.85 = 23.8
G2 긍정형 : 66 × 0.75 = 49.5
G3        : 43 × 0.80 = 34.4
                        ------
                        124.4건
```

### 7.4 결론

| 구분 | 건수 | 비율 |
|------|------|------|
| 판정 가능 (G1+G2+G3) | 154 | 69.1% |
| 재현율 반영 실효 커버리지 | 124 | **55.6%** |
| 확정 대기 (G4) | 18 | 8.1% |
| 구조적 불가 (G5) | 51 | 22.9% |

**현재 실효 커버리지는 약 56%다.**

초판이 제시한 41%(현재)와 64%(산출물 정비 후) 사이에 들어온다. 이유는 두 가지가 상쇄되었기 때문이다.

| 방향 | 사유 | 영향 |
|------|------|------|
| 상승 | ADR과 확정값이 이미 존재하고 저장소에 있다. 초판이 "앞으로 만들어야 한다"고 본 것이 이미 있었다 | +약 15%p |
| 하락 | 확정 스택에 Checkstyle, SpotBugs, ArchUnit이 없어 G1이 축소. 미정과 모순으로 G4 18건 발생 | -약 8%p |

#### 이 수치가 능력치이지 현황이 아니라는 점

**`LGU-2/backend` 저장소에는 현재 `README.md` 하나뿐이다.**
소스 코드도 `application.yml`도 없다. 즉 지금 게이트를 돌리면 판정 대상이 0건이다.

56%는 "코드가 있을 때 223건 중 몇 건을 판정할 수 있는가"이지 "지금 몇 건이 지켜지고 있는가"가 아니다.
`[인프라]` G2 25건이 특히 그렇다. 타임아웃, 커넥션풀, 헬스체크 설정은 확정값 문서에 완전한 yaml로 적혀 있지만 **아직 코드 저장소에 옮겨지지 않았다.**

### 7.5 커버리지를 올리는 방법

초판은 "ADR을 `docs/adr/`에 쌓는 것이 첫 번째 조치"라고 적었다. **그 전제는 틀렸다.**
ADR은 이미 34건이 있고 `LGU-2/infra`의 `docs/system-design/`에 있다. 만드는 작업이 아니라 이미 있는 것을 쓰는 작업이다.

남은 지렛대는 다음 셋이다.

| 조치 | 회복되는 항목 | 성격 |
|------|--------------|------|
| 미정 값을 부하 시험으로 확정 | G4 중 14건 | 측정 작업. 오토스케일링과 알람 임계 |
| 확정값 문서 간 모순 해소 | G4 중 4건 | 문서 정리. readiness 항목이 최우선 |
| 도구 스택 보강 (ArchUnit 등) | G2 중 6건이 G1로 이동 | 재현율 0.75에서 0.98로 상승 |

첫 두 조치로 G4 18건이 전부 G3로 올라가면 판정 가능이 172건(77.1%), 실효는 약 139건(62.3%)이 된다.

세 번째는 커버리지 항목 수를 늘리지는 않고 재현율만 올린다.
도메인 경계와 순환 참조는 ArchUnit이 확실하게 잡는 영역이라 LLM에 맡기는 것이 비효율적이다.

### 7.6 회복되지 않는 23%

G5 51건은 어떤 설계로도 회복되지 않는다.
인시던트 대응 문서의 훈련, 역할 분리, 비난 없는 문화는 사람이 실제로 하는 행위이고, LLM은 그 행위의 **기록 유무**까지만 볼 수 있다.
기록이 있다는 것과 훈련이 실제로 유효했다는 것은 다르다.

이 구간까지 커버한다고 주장하는 설계는 검증이 아니라 검증 시늉을 자동화하는 것이다.

또한 56%는 **항목 커버리지이지 결함 커버리지가 아니다.**
G5로 빠진 인시던트 대응 항목들은 건수로는 23%지만, 사고 발생 시 손실 규모로 보면 비중이 훨씬 크다.
이 설계는 사고의 23%를 방치하는 것이 아니라, 사람이 반드시 봐야 할 23%를 명시적으로 남겨 두는 것으로 이해해야 한다.

## 8. 측정 지표

| 지표 | 의미 | 기준 (등급 C) |
|------|------|---------------|
| 항목 커버리지 | 판정 시도된 항목 / 전체 223건 | 도입 6개월 내 56% (7.4절) |
| 지적 정확도 | 실제 수정으로 이어진 지적 비율 | 차단 항목 90%, 전체 70% |
| `INSUFFICIENT_EVIDENCE` 비율 | 앵커 규칙의 충실도 | 20% 이하 |
| 유출 결함 중 점검 항목 해당분 | 게이트를 통과했으나 사고로 이어진 건 | 추세 감소 |
| PR당 지적 건수 | 읽히는 양인가 | 10건 이하 |
| 게이트 우회 건수 | 차단을 건너뛴 병합 | 0건. 발생 시 사유 기록 |

가장 중요한 것은 네 번째 지표다.
게이트를 통과했는데 사고가 났다면, 그 항목의 재현율 가정이 틀렸다는 뜻이다.
7.2절의 등급 C 수치를 갱신하는 근거로 쓴다.

정확도만 보면 지적을 줄이는 방향으로 최적화된다.
재현율을 함께 보지 않으면 "아무것도 지적하지 않는 정확한 리뷰어"가 된다.

## 9. 집계 재현 방법

1장의 등급 A 수치는 다음으로 재현한다.

```bash
# docs/software-quality 에서 실행한다
# 이 문서 자신의 점검 항목은 집계 대상이 아니므로 제외한다
EX=--exclude=qa-llm-verification.md

for lv in 코드 설계 인프라 프로세스; do
  n=$(grep -h $EX "^\* \`\[$lv\]\`" qa-*.md | wc -l | tr -d ' ')
  neg=$(grep -h $EX "^\* \`\[$lv\]\`" qa-*.md | grep -c '않는가\|없는가')
  echo "$lv: 총 $n / 부정형 $neg / 긍정형 $((n-neg))"
done

echo "합계: $(grep -h $EX '^\* `\[' qa-*.md | wc -l | tr -d ' ')건"
```

```
코드: 총 65 / 부정형 21 / 긍정형 44
설계: 총 65 / 부정형 3 / 긍정형 62
인프라: 총 42 / 부정형 3 / 긍정형 39
프로세스: 총 51 / 부정형 5 / 긍정형 46
합계: 223건
```

제외 지정을 빠뜨리면 이 문서의 점검 항목 28건이 섞여 집계가 251건이 된다.

점검 항목을 추가하거나 옮기면 수치가 달라진다.
7장의 커버리지도 함께 재계산해야 한다. 갱신하지 않으면 오래된 비율이 근거처럼 인용된다.
